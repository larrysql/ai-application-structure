# AI 应用的结构 01｜只用 Python 和 AI，把一段文字变成结构化数据

过去几十年，软件开发一直遵循着一个基本逻辑：程序员编写规则，计算机执行规则。

如果我们希望程序判断一封邮件是不是垃圾邮件，就需要设计判断条件；如果希望程序从一段文字中提取信息，就需要编写解析逻辑。即使后来出现了机器学习，开发者仍然需要围绕特定任务收集数据、训练模型，并将模型集成到软件中。

大语言模型的出现，改变了这种开发方式。

今天，我们可以编写一个很简单的 Python 程序，把一段文字发送给大模型，再接收它返回的结果。原本需要大量规则才能处理的自然语言任务，现在可能只需要一次 API 调用。

这听起来有些不可思议。一个普通的 Python 程序，为什么只需要增加几行代码，就能表现出理解语言、分析问题甚至推理的能力？

要回答这个问题，我们需要拆开一次最普通的大模型 API 调用，看看它背后究竟发生了什么。

## 一、首先要理解：你的程序并没有真正拥有一个大模型

假设我们要开发一个简单的应用。

用户输入一句话：

“我做了十几年软件开发，现在想开发自己的 AI 产品，但又担心失去稳定收入。”

我们希望程序能够识别出这段话中的个人经历、未来目标和现实顾虑。

如果使用传统编程方法，可以尝试通过关键词匹配来实现。例如，出现“想”就判断为目标，出现“担心”就判断为顾虑。但这种方式很快会遇到问题。

“我不想继续做软件开发”和“我想继续做软件开发”，都包含“想”，含义却完全不同。语言中的否定、条件、上下文关系和隐含意义，很难依靠几个简单规则准确处理。

现在，我们可以把这段话交给大语言模型。

但这里有一个容易产生的误解：调用大模型 API，并不意味着我们把一个智能模型安装进了自己的程序。

实际上，我们的 Python 程序仍然只是一个普通程序。它没有突然获得数百亿个模型参数，也没有在本地执行复杂的神经网络计算。

真正的大模型运行在远程服务器上。我们的程序通过网络发送请求，由远程模型完成计算，再把结果返回给程序。

这与传统软件调用天气、地图或者支付接口，在通信方式上并没有本质区别。

真正不同的是：传统 API 通常提供明确、有限的功能，而大语言模型 API 提供的是一种能够根据输入内容生成不同结果的通用语言处理能力。

## 二、一次 API 调用究竟经历了什么？

我们先看整个过程。

```text
用户输入
   │
   ▼
Python 应用程序
   │
   │ 组织请求
   ▼
大模型 API 服务
   │
   │ 处理输入、运行模型推理
   ▼
生成输出内容
   │
   │ 返回响应
   ▼
Python 应用程序
   │
   │ 解析、检查、使用结果
   ▼
显示给用户或执行后续操作
```

这个过程可以分为三个部分。

第一部分发生在我们自己的程序中。程序接收用户输入，构造请求，决定使用哪个模型，并设置必要的参数。

第二部分发生在模型服务端。服务端处理输入，将文本转换为模型能够处理的 Token，运行模型推理，逐步生成输出 Token，再把它们转换为可以返回的内容。

第三部分重新回到我们的程序。程序接收响应，提取所需内容，判断是否需要进一步处理，然后决定如何使用这些结果。

这里最重要的一点是：**模型负责生成结果，应用程序负责决定结果如何被使用。**

大模型可以告诉我们，某句话可能表达了一个职业目标，但它并不会因此自动把这个目标保存到数据库。是否保存、如何保存、是否需要用户确认，都由应用程序决定。

理解这一点，是理解整个 AI 应用架构的起点。

## 三、动手实验：用 Python 调用一次大模型

现在，我们不再停留在概念上，而是编写一个真正可以运行的程序。

这个实验使用 Python 和 OpenAI API。选择它并不是因为 AI 应用只能使用 OpenAI，而是因为它提供了比较直接的模型调用接口，适合初学者理解整个过程。

首先，需要准备 Python 环境，并安装官方 SDK。

```bash
pip install --upgrade openai
```

然后在模型服务平台创建 API Key。

API Key 可以理解为调用接口时使用的身份凭证。服务端通过它识别调用者、检查权限并记录用量。它不应该直接写入准备公开的源代码，更不能提交到 GitHub。

可以先通过环境变量配置：

Windows PowerShell：

```powershell
$env:OPENAI_API_KEY="你的API密钥"
```

Linux 或 macOS：

```bash
export OPENAI_API_KEY="你的API密钥"
```

接下来创建一个文件 `hello_ai.py`。

```python
from openai import OpenAI

client = OpenAI()

response = client.responses.create(
    model="gpt-4.1-mini",
    instructions=(
        "你是一个信息分析助手。"
        "请识别用户描述中的经历、目标和顾虑，"
        "使用简洁中文回答。"
    ),
    input=(
        "我做了十几年软件开发，"
        "现在想开发自己的AI产品，"
        "但担心失去稳定收入。"
    )
)

print(response.output_text)
```

运行：

```bash
python hello_ai.py
```
### 第一次运行：模型真的回答了

在 Windows 环境下运行上述程序，API 调用成功。模型返回了以下内容：

> 大语言模型API是通过接口形式，向开发者提供强大的自然语言处理模型服务。开发者可以通过调用API，实现文本生成、理解、翻译、问答等功能，无需自行训练模型，大大简化应用开发过程。

这不是事先编写好的固定答案，而是程序向远程模型发送请求后，实际获得的响应。

程序还返回了两个值得关注的数据：

| 指标 | 实际结果 |
|---|---:|
| Input Tokens | 32 |
| Output Tokens | 54 |
| Total Tokens | 86 |

Token 是大语言模型处理文本时使用的基本单位。输入内容需要消耗 Token，模型生成回答同样需要消耗 Token。API 服务通常会根据模型类型及相关 Token 用量计算费用。

这次调用总共使用了 86 个 Token。对于如此简单的任务，消耗很少，但如果一个应用每天需要处理几十万次请求，Token 用量就会直接影响运行成本。

我们还可以观察到一个有意思的现象：Python 程序本身并没有任何解释“大语言模型 API”的业务规则，它只是把问题发送给模型，再将返回结果打印出来。

这正是 AI 应用与传统规则程序之间最直观的区别。



这里需要说明，模型的具体措辞可能每次有所不同。即使输入相同，大模型也不一定返回完全一致的文本。

另外，这段程序使用的是指定模型的 API 服务，实际运行会产生相应的 Token 用量和费用，具体价格应以服务商公布的信息为准。

到这里，我们已经完成了第一个 AI 应用实验。

但如果只是复制代码、看到输出，就认为自己理解了 AI 应用，显然还远远不够。

真正值得研究的，是这几行代码究竟做了什么。

## 四、为什么几行代码就能调用如此复杂的模型？

我们重点观察这一行：

```python
response = client.responses.create(...)
```

从 Python 的角度看，它只是一次方法调用。

SDK 会按照 API 的要求组织网络请求，将模型名称、输入内容和其他参数发送给服务端。它还负责处理认证、请求格式和响应解析等工作，因此开发者不需要手动编写所有 HTTP 通信细节。

在服务端，情况就复杂得多了。

首先，输入文字会经过 Tokenization，也就是分词元处理。模型并不是直接把整句话当成一个不可分割的对象来理解，而是把文本转换成一系列 Token。

这些 Token 再被映射成数字表示，经过模型内部的多层神经网络计算。

如果你读过《AI 的结构》系列，应该已经接触过 Token、Embedding、Attention 和 Transformer 等概念。这些技术共同构成了大语言模型处理信息的基础。

模型生成回答时，通常并不是一次性计算出完整文章，而是根据已有上下文，逐步预测接下来应该生成什么 Token。

生成一个 Token 后，它又成为后续生成的上下文的一部分。这个过程持续进行，直到达到停止条件。

最后，服务端把生成结果整理为 API 响应，发送回我们的程序。

我们在终端看到的，只是整个计算过程的最终输出。

这有点像调用数据库查询接口。程序员只需要执行一条 SQL，却不必在每次查询时亲自实现索引扫描、连接算法和缓冲区管理。

不过，两者之间存在一个关键区别。

数据库查询通常要求按照明确的数据与查询语义返回结果，而大语言模型生成的是基于模型参数和上下文计算出来的输出。它可能准确，也可能错误，还可能生成看起来合理、实际上却没有依据的内容。

因此，调用成功并不等于结果正确。

## 五、Prompt 究竟是什么？它为什么如此重要？

在刚才的程序中，我们提供了两部分内容。

第一部分是：

```python
instructions = (
    "你是一个信息分析助手。"
    "请识别用户描述中的经历、目标和顾虑。"
)
```

第二部分是：

```python
input = "我做了十几年软件开发……"
```

前者用于说明模型应该完成什么任务，后者提供需要处理的具体内容。

很多人把这些自然语言指令统称为 Prompt。

Prompt 的作用并不是修改模型内部已经训练好的参数，而是通过提供上下文，引导模型在当前任务中生成符合要求的结果。

这意味着，同一个模型可以通过不同的指令承担不同的工作。

例如，我们可以让它分析用户目标，也可以让它提取合同条款、总结技术文档、解释代码，或者生成一封邮件。

但 Prompt 不是传统意义上的程序代码。

我们写下“请准确识别用户目标”，并不意味着模型就获得了百分之百准确识别目标的能力。

同样，我们要求“不要编造信息”，也不意味着模型一定不会产生错误。

**Prompt 是对模型行为的引导，而不是对模型行为的绝对约束。**

这个区别，在开发真实 AI 产品时尤其重要。

## 六、第一次遇到 AI 应用的核心问题：结果不确定

我们不妨修改刚才的程序，让模型直接返回 JSON。

只需要把指令改成：

```python
instructions = """
分析用户输入，返回JSON格式。

字段包括：
- experience：个人经历
- goal：未来目标
- concern：现实顾虑

不要输出其他内容。
"""
```

### 第二次实验：让 AI 从自然语言中提取信息

接下来，我们尝试让模型完成一个稍微复杂的任务。

输入一段自然语言：

> 我做了十几年软件开发，现在想开发自己的 AI 产品，但担心失去稳定收入。

我们希望模型识别出其中的个人经历、未来目标和现实顾虑，并按照 JSON 格式返回。

运行 `extract_information.py` 后，模型给出了以下结果：

```json
{
  "个人经历": "做了十几年软件开发",
  "未来目标": "开发自己的AI产品",
  "现实顾虑": "担心失去稳定收入"
}
```

从内容上看，这次提取是成功的。模型正确区分了过去的经历、未来的目标和当前的顾虑，没有明显曲解原始输入。

但仔细观察终端输出，会发现一个容易忽略的问题：模型在 JSON 前后增加了 Markdown 代码块标记。

对于人类读者，这几乎没有影响。我们仍然能够清楚地理解模型返回的信息。

但对于计算机程序，情况就不同了。

如果直接使用 Python 的 `json.loads()` 解析整个响应，可能因为这些额外字符而失败。

这意味着，模型虽然理解了任务，也生成了正确的信息，却没有严格按照程序所需的数据格式返回结果。

**人类能够理解的正确回答，不一定是程序能够直接使用的有效数据。**

这也是 AI 应用开发中非常典型的问题。

我们不仅需要关心模型是否理解用户，还需要确保模型输出能够被后续程序可靠地处理。

需要注意的是，本次实验只测试了一条输入，不能据此判断模型在各种情况下的信息提取准确率。即使 JSON 格式完全正确，也不能保证其中的事实和推断一定正确。

后续实验将进一步研究如何通过结构化输出、Schema 校验和程序验证，提高 AI 应用的可靠性。

看起来已经非常接近一个真正的软件功能了。

因为 JSON 可以被程序解析，我们似乎可以直接把结果写入数据库。

但问题也恰恰从这里开始。

假设用户输入的是：

“我以前想开发自己的 AI 产品，但现在已经不打算做了。”

如果模型忽略了“以前”和“现在已经不打算”这两个关键条件，就可能错误地把“开发 AI 产品”识别为用户当前目标。

更麻烦的是，即使返回了合法 JSON，也不能证明其中的信息是真实、准确的。

这实际上涉及两个不同层次的问题。

第一个是格式正确性：模型是否按照我们要求的结构返回数据。

第二个是语义正确性：模型是否真正理解了用户的意思。

对于格式问题，我们可以使用 JSON Schema、结构化输出、类型校验等技术提高可靠性。

但对于语义问题，仅仅依靠 JSON 格式远远不够。我们还需要测试、校验，必要时让用户确认。

因此，真正的 AI 应用不能简单地理解为：

用户输入 → 大模型 → 数据库。

更可靠的设计应该是：

```text
用户输入
   ↓
大模型分析
   ↓
结构化输出
   ↓
程序校验
   ↓
必要时用户确认
   ↓
写入数据库
```

这也是为什么一个看起来只需要十几行代码就能实现的 AI 功能，在真正进入生产环境之后，可能需要数百行甚至更多代码来处理异常、验证结果、管理权限和维护数据一致性。

## 七、AI 应用开发与传统软件开发，究竟有什么不同？

通过这个简单实验，我们已经能够发现一些变化。

传统软件开发的主要任务，是把业务规则转换成可以执行的程序逻辑。输入符合什么条件，就执行什么操作，程序的行为通常由开发者明确规定。

AI 应用开发则引入了一个新的组成部分：具有一定语言理解和生成能力，但输出并不完全确定的模型。

这使得软件系统能够处理过去难以用固定规则描述的问题，同时也带来了新的工程挑战。

过去，我们主要关注代码是否正确、数据库是否一致、接口是否稳定。

现在，还必须关注模型是否理解任务、是否产生错误推断、输出能否被程序可靠处理、调用成本是否可控，以及模型版本变化会不会影响原有功能。

AI 并没有让软件工程变得不重要。

恰恰相反，当我们把一个不完全确定的模型引入软件系统时，传统软件工程中的数据校验、权限控制、测试、日志和异常处理，反而变得更加重要。

从这个意义上说，AI 应用开发不是对传统软件开发的简单替代，而是在原有软件架构中增加了一种新的计算能力。

程序员不再需要为所有语言处理任务亲自编写完整规则，但仍然需要设计系统，决定模型可以做什么、不能做什么，以及如何判断它做得是否正确。

## 八、一个 AI 应用真正的价值在哪里？

现在回头看我们最初的问题。

为什么一个普通的 Python 程序，只需要几行代码，就能表现出语言理解能力？

因为真正复杂的模型能力，已经由远程服务提供。我们的程序通过 API 接入这种能力，再将它用于具体任务。

但这也意味着，任何能够访问相同 API 的开发者，都可以编写类似的调用程序。

如果一个产品的全部功能只是把用户输入发送给模型，再把回答显示出来，那么它的技术门槛可能并不高。

真正有价值的 AI 应用，需要解决模型本身没有替我们解决的问题。

例如，如何理解特定业务的数据？如何长期保存用户信息？如何处理互相矛盾的历史记录？如何安全地调用外部工具？如何判断模型生成的结论是否可靠？如何让系统在多次使用之后仍然保持一致性？

这些问题无法单纯依靠增加一个 Prompt 来解决。

它们需要数据库、业务逻辑、软件架构、测试体系和用户体验共同发挥作用。

也正是在这里，AI 应用开发开始与传统软件工程真正结合。

## 结语：从调用模型，到构建系统

这篇文章，我们只做了一件非常简单的事情：使用 Python 调用一次大语言模型 API。

但通过这个实验，可以建立对 AI 应用最基本的认识。

大模型不是我们的应用程序本身，而是应用可以调用的一种能力。Prompt 用于描述任务，API 用于连接模型，程序负责处理结果，而完整的软件系统负责确保这些能力能够被可靠、安全地使用。

调用模型，只是 AI 应用开发的起点。

真正困难、也真正有意思的部分，是如何把这种具有不确定性的智能能力，放进一个需要稳定运行的软件系统中。
